怎么配置

配置这件事本质上只有一句话：告诉 Host「怎么找到并启动 / 连接一个 server」。剩下的都是这句话的两种写法。

第 5 册 · 基于 MCP 规范 2026-07-28
本册要解决的问题

「配置了之后 Agent 可以访问一些资源」—— 这一册把这个「配置」拆开：文件放在哪、里面写什么、两种形态有什么区别、为什么配了没生效。

1配置的本质

Host 需要知道一件事才能用上某个 server：怎么把它弄起来，或者怎么连上它。

就这一件事，落在配置文件里只有两种写法，取决于这个 server 跑在哪里：

  • Server 在本机 → Host 负责启动它，当作一个子进程，走 stdio 通信。配置里写「用什么命令启动它」。
  • Server 在远端 → Host 直接连接它，走 HTTP 通信。配置里写「它的地址是什么」。

除此之外的字段（环境变量、请求头）都只是这两件事的补充。

2统一结构

几乎所有 Host 都读同一种 JSON 结构：顶层一个 mcpServers 键，值是「服务器名 → 服务器定义」的映射。

JSON · 通用骨架 
{
  "mcpServers": {
    "服务器名": {
      ... 服务器定义 ...
    }
  }
}

服务器名是你自己起的标签，但它有三个实际作用：显示在 Host 的界面里；出现在工具名中（例如 mcp__github__list_issues）；同一个文件里必须唯一，重名会静默覆盖。

形态一：stdio（本地进程）

JSON 
{
  "mcpServers": {
    "my-server": {
      "command": "node",
      "args": ["/absolute/path/to/index.js"],
      "env": {
        "API_KEY": "sk-..."
      }
    }
  }
}
字段含义必需
command要执行的可执行文件，不是 shell 命令字符串。要用 shell 就写 bash 或 cmd，把脚本放进 args。是
args传给命令的参数数组。是（可为空数组）
env额外注入的环境变量。会叠加在 Host 自己的环境变量之上，适合放 API token 和配置开关。否

形态二：Streamable HTTP（远端服务）

JSON 
{
  "mcpServers": {
    "github": {
      "url": "https://mcp.example.com/github",
      "headers": {
        "Authorization": "Bearer ${GITHUB_MCP_TOKEN}"
      }
    }
  }
}
字段含义必需
urlServer 的地址。看到 url 就说明这是远端 server。是
headers每个请求附带的 HTTP 头，常用于 Authorization 传 token。否
三条最容易踩的规则

一、用绝对路径。相对路径是相对 Host 的工作目录解析的，而那个目录往往不是你以为的那个。写死绝对路径能消掉一大类「我这里能跑」的问题。

二、command 是可执行文件，不是 shell 字符串。写 "command": "npx -y foo" 是错的，要写成 "command": "npx", "args": ["-y", "foo"]。

三、改完要重启 Host。server 是 Host 在启动时拉起来的，改配置不重启不生效（Claude Desktop 要完整退出，关窗口不算）。

3各 Host 的文件位置

结构一样，只是文件放在不同的地方。下表是常见 Host 的对照（路径可能随版本变化，以各自官方文档为准）：

Host配置文件位置特点
Claude Desktop Windows：%APPDATA%\Claude\claude_desktop_config.json
macOS：~/Library/Application Support/Claude/claude_desktop_config.json
Linux：~/.config/Claude/claude_desktop_config.json 		单一全局配置，每个会话看到的都一样。UI 里 Settings → Developer → Edit Config 可以直接打开。
Claude Code 项目级：<项目根>/.mcp.json
用户级：~/.claude.json 		分三层，可提交进 git 共享给团队；工具名带 mcp__服务器名__工具名 前缀。
Cursor 全局：~/.cursor/mcp.json
项目级：<项目根>/.cursor/mcp.json 		项目级配置适合绑定某个代码库专用的 server。
VS Code 工作区：<项目根>/.vscode/mcp.json
用户级：命令面板搜 MCP: Open User Configuration 		支持从其他应用发现配置；本地 stdio server 可以沙箱化，限制它能访问的路径和域名。
WorkBuddy Windows：C:\Users\<你>\.workbuddy-ai\mcp.json 顶层同样是 mcpServers；写完后需要在连接器管理页面的自定义连接器入口点「信任」才会启用。
为什么都是 JSON

因为这份配置本来就是「启动参数」的序列化形式。Host 读到之后，做的事情就是 spawn(command, args, {env}) 或者发一个 HTTP 请求。理解到这一层，配置就不再神秘了。

4三个真实例子

例一：文件系统（最简单的冒烟测试）

通过文件系统工具，让助手访问配置允许的目录。目录范围需要由 server 在每次操作时检查；配置允许目录本身，不等于给整个进程加上了操作系统沙箱。

JSON 
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-filesystem",
        "/Users/me/projects",
        "/Users/me/notes"
      ]
    }
  }
}

末尾那些路径参数，就是允许服务器访问的根目录。精确列出你要暴露的，不要多列。

例二：GitHub（用 env 传 token）

JSON 
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_你的token"
      }
    }
  }
}

建 token 时只勾你真正需要的 scope。把 token 当密码对待 —— 绝不要把带真实 token 的配置提交进仓库。

例三：Postgres（连接字符串作为参数）

JSON 
{
  "mcpServers": {
    "postgres": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-postgres",
        "postgresql://readonly_user:password@localhost:5432/mydb"
      ]
    }
  }
}

数据库场景的要点：优先用只读角色；schema 命名要清晰（模型靠读 schema 决定怎么写查询）；绝不要把生产环境的写用户交给模型。

5优先级与覆盖

Claude Desktop 只读一份文件，简单。Claude Code 这类工具支持多层叠加，这是新用户最容易困惑的地方：

层级位置用途优先级
企业托管由 MDM / 企业设置推送公司统一分发，强制生效最高（不可覆盖）
项目级<项目根>/.mcp.json团队共享，提交进 git高
用户级~/.claude.json个人常用，跨项目可用低

合并规则：同一个服务器名，高层覆盖低层。这样既能让团队配置优先于个人配置，也让公司推的强制配置无法被个人绕过。

6stdio 还是 HTTP

stdio（本地）Streamable HTTP（远端）
配置字段command / args / envurl / headers
Server 在哪本机，Host 拉起为子进程独立的机器 / 云端服务
鉴权无（同机进程）需要，通常 OAuth 2.1 + Bearer token
能否共享不能，每个 Host 各起一份能，多 Host 可同时连
适合个人本地工具团队共享、SaaS、被多个 Host 复用
选择原则

个人本地工具 → stdio 永远够用。要团队共享、或一个 server 被多个 Host 同时用 → HTTP。判断标准很简单：这个 server 需要跨机器吗？

7排错清单

服务器死活加载不出来时，按这个顺序查：

  1. JSON 能解析吗？一个多余的逗号或缺失的括号，会让整个文件里所有 server 失效。丢进任意 JSON 校验器过一遍。
  2. 路径是绝对且正确的吗？把配置里的完整命令复制到终端里直接跑。终端跑不通，Host 里必然也跑不通。
  3. 依赖装了吗？npx -y <包> 首次运行要联网下载。内网环境先全局装好。
  4. 环境变量设了吗？缺 token 的 server 会启动成功，但在第一次调用时才失败。
  5. server 往 stderr 打印了什么？先读日志再猜。stdio 传输下，日志只能走 stderr。
  6. 版本匹配吗？如果某个 server 是按旧协议版本写的，可以在 args 里把版本钉死。
  7. 重启了吗？改完配置没重启 Host，等于没改。
一个高频故障

如果你在写 server 时用了 print() / fmt.Println() 做调试输出，那些内容会混进 stdout，把协议流污染掉，Host 直接解析失败。所有调试输出必须走 stderr。这是自己写 server 时第一个会撞上的坑。

8一句话总结

第 5 册 · 一句话总结

配置的本质是告诉 Host「怎么启动或连接一个 server」；所有 Host 都用同一套 mcpServers JSON 结构，本地 server 写 command/args/env，远端 server 写 url/headers；差别只在文件放在哪、以及是否分层覆盖；配置不生效时，先校验 JSON、再在终端里手跑一遍命令、再看 stderr 日志。
