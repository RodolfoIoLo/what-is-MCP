角色与结构

Host、Client、Server 各自负责什么；协议被切成哪两层；Server 能对外暴露哪三种东西，以及它们的区别到底在哪。

第 2 册 · 基于 MCP 规范 2026-07-28
本册要解决的问题

第 1 册给了三个角色的名字，但没讲它们各自干什么。这一册把结构画清楚 —— 特别是「Server 暴露的三种东西（工具 / 资源 / 提示）到底有什么区别」，这是理解 MCP 最重要的一道坎。

1三个角色各自的职责

Host（主机）

Host 是用户直接面对的那个 AI 应用。它的职责是「编排」，具体包括：

  • 管理连接：知道要连哪些 Server，为每个 Server 创建并持有一个 Client。
  • 聚合能力：把所有 Server 提供的东西汇总成一份清单，交给模型。
  • 驱动模型：把用户的问题 + 聚合后的能力清单一起送给模型，由模型决定要不要调用。
  • 执行调用：模型决定调用某个工具后，Host 通过对应的 Client 把请求发给对应的 Server。
  • 把关与呈现：在把用户数据发给 Server 之前征得同意；把 Server 返回的结果回填给模型；把最终答案呈现给用户。

注意最后两条 —— Host 是那个「负责安全和用户体验」的角色。协议本身不做权限判断，判断权在 Host 手里。

Client（客户端）

Client 不是独立程序，它是 Host 内部的一个对象 / 组件。它和 Server 是一对一的：一条连接一个 Client。职责是：

  • 建立并维持到某一个 Server 的连接。
  • 把 Host 的意图翻译成 MCP 消息发出去。
  • 接收 Server 的响应和通知，交给 Host。
  • 代表 Host 向 Server 声明「我这边支持什么」（客户端能力，见第 5 节）。

Server（服务器）

Server 是能力提供方。职责是：

  • 声明自己提供哪些能力（哪些工具、哪些资源、哪些提示）。
  • 接收调用请求，执行实际操作（读文件、查数据库、调 API……），返回结果。
  • 在需要的时候，反过来向 Client 请求信息（例如向用户确认，见第 4 节）。
「Server」这个词有个坑

MCP 里的 Server 指「提供能力的程序」，和它跑在哪里无关。它可能是一个跑在你本机、由 Host 拉起来的进程（用 stdio 传输），也可能是一个跑在云端、被很多 Host 同时连接的 HTTP 服务。

所以当你听到「MCP Server」时，先别假设它是网络服务 —— 大多数你日常配置的其实是本地进程。

2两层架构

MCP 规范把自己分成两层，理解这个分层能解释很多困惑。

层负责什么包含
数据层（Data layer） 消息的内容：怎么声明能力、怎么调用、怎么返回、方法叫什么名字 JSON-RPC 2.0 消息格式、能力协商、三种原语、通知
传输层（Transport layer） 消息的通路：字节怎么从一端到另一端、连接怎么建立、授权怎么做 stdio（标准输入输出）、Streamable HTTP

概念上，数据层是内层，传输层是外层：数据层的内容被装进传输层送出去。换传输方式，数据层的消息一个字都不用改。

为什么要分这两层

因为「本地进程之间」和「跨网络的远端服务」需要的通路完全不同：前者用管道最省事，后者必须走 HTTP。把内容（数据层）和通路（传输层）分开，同一套消息格式就能同时服务这两种场景，也让「本地 server 改造成远端 server」变成只换传输层的事。

3服务端三种原语

原语（primitive）是规范里的术语，指「协议规定的、可以被暴露出来的基本能力单元」。Server 可以暴露三种：

Tools（工具）

由模型决定

可被执行的函数。它做一件事，有输入参数，有返回值。比如「读某个文件」「执行一条 SQL」「创建一个 issue」。

工具是三种原语里唯一「会产生副作用」的（可能写文件、改数据库、发请求），所以也是安全上最需要小心的。

发现：tools/list  ·  执行：tools/call

Resources（资源）

由应用决定

可被读取的数据。它没有参数、不执行动作，只是「把一份内容交出来」。比如「某个文件的内容」「数据库的表结构」「某个 API 的响应」。

资源是只读的、被动的内容来源。每个资源有一个 URI 标识（例如 file:///notes/todo.md）。

发现：resources/list  ·  读取：resources/read

Prompts（提示模板）

由用户决定

可复用的消息模板。它本身不执行也不返回数据，而是产出「一段可以直接送进模型的话」，通常带占位参数。比如一个「代码审查」模板，参数是文件路径，产出是结构化的审查指令。

它面向的是用户：用户在界面上主动选择一个模板来发起对话，而不是模型自己决定。

发现：prompts/list  ·  获取：prompts/get

三者的区别：看「谁决定」

很多人分不清这三种，是因为从「功能」角度看它们都能给模型提供东西。真正的区别在控制权：谁来决定这个东西被用上。

原语形态谁决定使用典型场景
Tools 可执行函数 模型自己判断该不该调 「帮我把这条待办标记完成」
Resources 可读取数据 Host 应用决定把哪些塞进上下文 「把当前打开的文件作为背景资料」
Prompts 消息模板 用户主动选择 「用『代码审查』模板，参数是这个文件」
一个例子把三者串起来

假设一个「数据库」Server：

它暴露 工具「执行只读查询」—— 模型看到用户问「上个月销售额多少」，自己决定调用它。
它暴露 资源「数据库表结构」—— Host 应用在会话开始时把表结构塞进上下文，让模型知道有哪些表。
它暴露 提示「写一条分析查询」—— 用户在界面上点这个模板，输入「分析退货率」，生成一段结构化的指令。

三种原语在同一个 Server 里并存，各管一摊。

4客户端原语

反过来，Client 也可以向 Server 声明能力。这就是第 1 册提到的「MCP 是双向的」的含义。

原语方向作用状态
Elicitation（征询） Server → Client → 用户 Server 在执行过程中需要额外信息时（例如「这个操作要确认吗」「缺一个参数」），向用户发起提问 可用
Sampling Server → Client Server 想借 Client 的模型做一次生成 已弃用（2026-07-28 起）
Roots Client → Server Client 告诉 Server「我的工作目录边界在哪」 已弃用
Logging Server → Client Server 向 Client 发日志 已弃用
为什么这里要提「已弃用」的

因为你在网上会大量看到 Sampling、Roots、Logging 的介绍，很多教程把它们当核心概念讲。它们在 2026-07-28 版被标记为弃用（有至少 12 个月的过渡期，仍然能用，但新实现不该再用）。

规范给出的替代方案：Sampling 建议直接集成模型厂商的 API；Logging 建议写到 stderr 或用 OpenTelemetry。你现在开始学，只需要重点掌握 Elicitation 这一个客户端原语。

5能力协商

两端连上之后，需要互相知道「你会什么」。这个动作叫能力协商（capability negotiation）。

在 2026-07-28 版里，协商不是一次性的握手，而是每个请求自己带着：

  • 客户端在每一个请求里，通过 _meta 字段声明自己的版本、身份和能力（比如「我支持 Elicitation」）。
  • 服务端的能力通过一个叫 server/discover 的方法获取。客户端可以在正式发请求前先调它一次，拿到服务端支持哪些能力、哪些协议版本；也可以不调，直接发请求，遇到不支持再说。
JSON · server/discover 的返回（节选） 
{
  "capabilities": {
    "tools":     { "listChanged": true },
    "resources": { "listChanged": true },
    "prompts":   { "listChanged": false }
  },
  "supportedVersions": ["2026-07-28"],
  "serverInfo": { "name": "my-db-server", "version": "1.0.0" }
}

读法：这个 Server 支持 tools 和 resources，且当工具或资源列表变化时会主动通知；支持 prompts 但不发变更通知。它只支持 2026-07-28 这一个协议版本。

为什么要协商

因为 Server 不是什么都得实现。一个只读的文档 Server 可能只提供 resources，不提供 tools。客户端必须知道对方到底有什么，才能正确地组织后续请求 —— 总不能对着一个不支持 tools 的 Server 去调 tools/list。

同时，协议本身在演进（有多个日期版本），协商也是双方对齐「用哪个版本说话」的机制。

6一句话总结

第 2 册 · 一句话总结

MCP 有三个角色：Host 是 AI 应用本体、Client 是 Host 内与单个 Server 一对一的连接组件、Server 是能力提供方；协议分两层 —— 数据层规定消息内容（JSON-RPC），传输层负责把消息送出去（stdio 或 Streamable HTTP）；Server 对外暴露三种原语，Tools 由模型决定调用、Resources 由应用决定读取、Prompts 由用户主动选择，区别不在功能而在控制权；Client 也能反向声明能力，当前可用的只有 Elicitation。
