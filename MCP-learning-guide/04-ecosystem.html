生态全景

梳理 MCP 生态中的不同角色：各类项目分别实现哪一部分，以及这些能力可以用在哪些场景。

第 4 册 · 基于 MCP 规范 2026-07-28
本册要解决的问题

不同项目提到的“MCP”可能处在不同层次。这一册按层梳理整个生态，列出各层的实现者，并介绍五类具体场景，包括配置现成服务、开发服务，以及在自己的应用中接入服务。

1困惑的根源

理解 MCP 生态时，首先要分清讨论的层次。同一个「MCP」，在不同语境下可能指：

  • 一份规范文档（协议本身）
  • 一个SDK 库（pip install mcp 装的那个东西）
  • 一个Host 产品的功能（「我们支持 MCP」）
  • 一个具体的 Server 程序（「装个 github MCP」）
  • 一个中间件（「我们的 MCP 网关」）
  • 一个扩展（「MCP 的 Tasks 扩展」）

它们全都有道理，只是层次不同。把层次理清，困惑自然消失。

2生态分层地图

3谁在实现 Host

Host 是那个「用户直接面对」的 AI 应用。下面这些产品都能充当 Host —— 也就是「能在里面配置 MCP server」：

类别具体产品说明
桌面 AI 助手 Claude Desktop、ChatGPT 桌面版 读一份全局配置文件，服务器对所有会话生效
终端编码工具 Claude Code 支持项目级配置（可提交进 git）与用户级配置分层
编辑器 / IDE VS Code（Copilot）、Cursor、Windsurf、Zed 按项目配置，工具名通常带 mcp__服务器名__工具名 前缀
Agent 框架 各种自研或开源的 Agent 框架 框架代码里实现 MCP client，把工具转给自家模型
你自己的程序 你写的 Python / Go 程序 用 SDK 里的 Client 类，直接连别人的 Server（第 6、7 册会写）
「支持 MCP」的两种含义

一个产品说「支持 MCP」，可能是指它能当 Host（连别人的 server），也可能是指它自己是一个 Server（被别人连）。听到这句话时，问清楚是哪一种。

4谁在实现 Server

Server 才是「能力」真正所在的地方。按来源分四类：

来源典型例子用途
官方参考实现 filesystem、fetch、git、memory 等 示范性质，也是日常最常用的基础能力。文件系统 server 几乎是所有人的第一个 MCP 配置。
SaaS 厂商 GitHub、Sentry、Stripe、Notion、Linear、Postgres 托管服务…… 厂商把自己的 API 包装成 MCP server，让任何 Host 都能接进来
企业内部自建 公司内部的 Jira、数据仓库、发布系统、监控平台 把内部系统统一接进 AI 工具，不用每个团队各写一套
个人自建 你自己的脚本、你常查的数据库 把私人工作流接进 AI 应用 —— 这就是第 6、7 册要写的

5五类使用场景

下面这五类覆盖了「MCP 具体能干什么」，也回答了「怎么自用 / 怎么给别人用」。

场景 A · 自用：把本地环境接进 AI 应用

你是使用者

你在 Claude Desktop / Cursor 里配置几个现成的 server，让 AI 能读你的笔记目录、查你本地的数据库、访问你的浏览器书签。不需要写任何代码，只是改一份 JSON 配置文件。

这是绝大多数人接触 MCP 的第一步，也是第 5 册的内容。

场景 B · 给别人用：把自家 API 包装成 server

你是提供方

你有一个服务或 API，想让它能被各种 AI 应用调用。写一个 MCP server 暴露它，用户只要在你的 server 地址上配一下就能用 —— 不需要为 Claude、Cursor、VS Code 各写一套插件。

SaaS 厂商走的都是这条路。这是 MCP 商业价值最直接的地方。

场景 C · 企业内部：统一接入内部系统

你是平台团队

公司里有一堆内部系统（工单、发布、监控、数据仓库）。为每个系统写一个 MCP server，员工在自己的 AI 工具里配上，就能用自然语言操作这些系统。

这一层通常还会配合中间层做统一鉴权和审计。

场景 D · 作为 Host 开发者：在自己的程序里接入别人的 server

你是开发者

你在写一个 Agent 程序，想让它能用社区里现成的 server。用 SDK 里的 Client，连上 server，把它的工具转成模型 API 的 function calling 参数。

这就是「Agent 怎么用 MCP」的本质，第 6 册会写完整闭环。

场景 E · 中间层：统一治理

你是运维 / 平台

企业里 MCP server 一多，就需要统一管：谁能访问哪个 server、调用要记日志、要限流、要防止敏感数据外流。于是出现了 MCP 网关和注册中心。

6中间层在做什么

中间层不是协议规定的角色，是生态自己长出来的。它插在 Client 和 Server 之间，对两端都伪装成对方。

类型做什么为什么需要
MCP 网关 转发 MCP 流量，在转发时做鉴权、限流、审计、脱敏 企业要统一管控所有 AI 对外部系统的访问
注册中心 维护一份「有哪些 server 可用、地址是什么」的目录 让用户不用手抄 URL，直接发现和安装
协议代理 把一种接口形态转换成 MCP（例如把一个老 REST API 包成 MCP） 存量系统不想改，用代理包一层

第 3 册提到的 Mcp-Method / Mcp-Name 请求头，就是专门为这类中间层设计的 —— 让网关不用解析 JSON 正文就能路由和鉴权。

7扩展机制

核心协议保持精简，更复杂的能力放进扩展（extension）。扩展是可选的，需要在两端都支持时才启用。目前主要的几个：

扩展解决什么问题
Tasks 长任务（批量处理、深度检索、长时间编译）会超过 HTTP 超时。这个扩展让 server 返回一个任务句柄，客户端可以轮询进度、中途补参数。
MCP Apps 让 server 能在 Host 界面里内联渲染交互式 UI（数据可视化、审批按钮），适合「人机协作」场景。
Skills over MCP 面向 agent 工作流的结构化指令包。
EMA（企业托管授权） 企业统一管理授权。

扩展用反向域名标识符命名，有各自的仓库和版本，可以独立演进而不动核心协议。

8一句话总结

第 4 册 · 一句话总结

MCP 生态分六层：Host（AI 应用）、协议、Server（能力提供方）、真实世界，外加贯穿两侧的 SDK 层，以及插在通路上的中间层与扩展层；「到处都在设计 MCP」只是因为不同的人在不同层上工作 —— 有人配 server、有人写 server、有人写 SDK、有人做网关；对个人来说，MCP 的用法就三类：配置现成的 server 自用、写 server 给别人用、在自己的程序里当 Host 去连别人的 server。
