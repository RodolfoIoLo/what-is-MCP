协议与报文

把「MCP 是个协议」这句话落到实处：一条消息长什么样、有哪些字段、怎么发出去、怎么传回来。

第 3 册 · 基于 MCP 规范 2026-07-28
本册要解决的问题

前两册讲的是「结构」，这一册打开黑盒看「内容」。读完你会知道：一条 MCP 消息就是一个 JSON 对象；调用一个工具，本质上就是发两个 JSON 对象；所谓「无状态」是指每个请求自带全部信息。

1JSON-RPC 的三种报文

MCP 的消息格式直接用 JSON-RPC 2.0。这个规范很简单，只有三种形态的消息：

① 请求 Request

带 id，发出后期待一个响应。四个字段：

  • jsonrpc：固定字符串 "2.0"
  • id：这次请求的编号，响应用同一个编号回来配对
  • method：要调用的方法名，如 "tools/call"
  • params：参数对象（可选）

② 响应 Response

带同一个 id，且要么有 result，要么有 error，不会同时有：

  • id：与请求相同
  • result：成功时的返回值
  • error：失败时的错误对象（含 code 和 message）

③ 通知 Notification

和请求长得一样，但没有 id。没有 id 就意味着「不需要回答」—— 发出方发完就完事。服务端告诉客户端「工具列表变了」就是用这种消息。

为什么要区分「请求」和「通知」

因为有些消息需要结果（「查一下有哪些工具」），有些不需要（「我这边工具列表更新了，通知你一声」）。用「有没有 id」来区分，就不用为两种语义设计两套格式。

2一次 tools/list 的完整往返

下面是最真实的一次「问服务端有哪些工具」。注意 _meta 字段 —— 它就是「无状态」的载体，后面第 4 节详细讲。

JSON · 客户端发出请求 
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": {
        "name": "my-client", "version": "1.0.0"
      },
      "io.modelcontextprotocol/clientCapabilities": {
        "elicitation": {}
      }
    }
  }
}
JSON · 服务端响应 
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [
      {
        "name": "query",
        "title": "执行只读查询",
        "description": "对一个 SQLite 数据库执行只读 SQL 查询，返回结果集",
        "inputSchema": {
          "type": "object",
          "properties": {
            "sql": { "type": "string", "description": "要执行的 SQL 语句" }
          },
          "required": ["sql"]
        }
      },
      {
        "name": "list_tables",
        "title": "列出所有表",
        "description": "列出数据库中的所有表名",
        "inputSchema": { "type": "object", "properties": {} }
      }
    ]
  }
}

几个要点：

  • inputSchema 是标准的 JSON Schema。Host 会把它原样翻译成模型能理解的「工具定义」（各家模型 API 的 function calling 参数就是这个形状）。
  • title 和 description 是给模型看的自然语言说明 —— 模型靠它来决定该不该调用这个工具。写得不清楚，模型就会用错。
  • 响应里只有 result，没有 error。两者互斥。

3一次 tools/call 的完整往返

JSON · 客户端调用工具 
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "query",
    "arguments": { "sql": "SELECT count(*) AS n FROM orders" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": { "name": "my-client", "version": "1.0.0" }
    }
  }
}
JSON · 服务端返回结果 
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [
      { "type": "text", "text": "n\n42" }
    ],
    "isError": false
  }
}

注意这里有两个层次的「成功 / 失败」，别混淆：

  • 协议层：请求本身有没有被正确处理。如果 method 写错了，返回的是 error 对象。
  • 业务层：工具执行的结果是不是成功。SQL 语法错误属于这一层 —— 协议层是成功的（result 正常返回），但 result.isError 为 true，content 里是错误信息。
为什么要分成两层

因为「工具执行失败」这件事，需要被模型看到。模型看到「SQL 写错了，报错是 xxx」，才能自己改一版重试。而协议层的错误（比如方法不存在）是编程错误，模型看到也没用。所以业务错误被塞进正常的 result 里，当成内容回给模型。

4无状态与 _meta

这是 2026-07-28 版最大的改动，也是你读旧教程最容易困惑的地方。

旧模型（2025-11-25 及更早）：先握手，再对话

客户端连上之后，必须先发一个 initialize 请求，服务端回一个 initialized。这次握手确定双方版本和能力，服务端随后发一个 Mcp-Session-Id，之后每个请求都要带上这个 id。连接是有状态的。

新模型（2026-07-28）：每个请求自带全部信息

握手没了，会话 id 也没了。每一个请求都是自包含的 —— 它自己在 _meta 里带上「我用的是哪个协议版本、我是谁、我支持什么能力」。服务端收到就能独立处理，不需要记住之前发生过什么。

_meta 里的键含义
io.modelcontextprotocol/protocolVersion 本次请求使用的协议版本，如 "2026-07-28"
io.modelcontextprotocol/clientInfo 客户端名称与版本，用于调试和兼容判断
io.modelcontextprotocol/clientCapabilities 客户端支持哪些能力，如 {"elicitation": {}}
无状态带来的实际好处

任何一条请求都可以落在负载均衡后面的任意一个实例上，不需要共享会话存储，也不需要粘性路由。对服务端部署来说是质的简化 —— 一个 MCP Server 变成了一个普通的 HTTP 无状态服务。

如果 Server 确实需要跨调用保持状态（比如「先打开一个游标，再分页取」），规范的建议是：让工具返回一个显式的句柄，让模型在后续调用里把它当参数传回来。这样状态是可见的、可审计的，而不是藏在传输层里。

版本不匹配会怎样

如果服务端不支持请求里声明的版本，它返回一个 UnsupportedProtocolVersionError，并在错误里列出自己支持的版本。客户端可以换一个双方都支持的版本重试。

JSON · 版本不支持时的错误 
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32004,
    "message": "Unsupported protocol version",
    "data": { "supported": ["2026-07-28", "2025-11-25"] }
  }
}

5传输层怎么分帧

数据层的消息是一个个 JSON 对象，但传输层看到的是字节流。所以需要一个规则回答：「从哪里到哪里算一条消息」。两种传输各有各的规则。

stdio：一行一条消息

Server 由 Host 作为子进程启动，双方通过标准输入 / 标准输出通信。规则非常简单：一个 JSON 对象占一行，以换行符 \n 结束，且 JSON 内部不能有裸换行。

字节流（换行符已标出） 
{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}\n
{"jsonrpc":"2.0","id":1,"result":{"tools":[...]}}\n
{"jsonrpc":"2.0","method":"notifications/tools/list_changed"}\n

几个实际要点：

  • stdout 只准放 MCP 消息。调试用的 print / fmt.Println 必须写到 stderr，否则会污染协议流，让 Host 解析失败。这是新手最常见的坑之一。
  • 没有网络开销，本地进程间通信，性能最好。适合「Server 和 Host 在同一台机器」的场景。

Streamable HTTP：POST + 请求头

Server 是一个独立的 HTTP 服务。客户端用 POST 把消息发过去。2026-07-28 版新增了强制要求的路由头：

HTTP 
POST /mcp HTTP/1.1
Host: mcp.example.com
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: query

{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"query","arguments":{"sql":"..."}}}

为什么要加 Mcp-Method 和 Mcp-Name 这两个头？因为网关、限流器、WAF 可以在不解析 JSON 正文的情况下就知道这条请求要干什么 —— 直接按头来路由、计费、鉴权。这对企业部署很重要。

响应可以是普通的 JSON，也可以是 text/event-stream（SSE）流式返回 —— 后者用于需要持续推送的场景。

6方法名总表

把协议里所有核心方法列成一张表。方向一栏：C→S 表示客户端发给服务端，S→C 反之。

方法名方向用途
server/discoverC→S查询服务端支持的协议版本、能力、身份（可选，但推荐先调）
tools/listC→S列出所有工具
tools/callC→S调用某个工具
resources/listC→S列出所有资源
resources/readC→S读取某个资源的内容
resources/templates/listC→S列出资源模板（带参数占位的资源，可选）
prompts/listC→S列出所有提示模板
prompts/getC→S获取某个提示模板填充后的内容
elicitation/createS→C服务端请求用户补充信息（走多轮往返，见下）
subscriptions/listenC→S打开一个长连接，订阅服务端的变化通知
notifications/tools/list_changedS→C通知：工具列表变了
notifications/subscriptions/acknowledgedS→C通知：订阅已确认

关于「多轮往返」（MRTR）

有一种情况：工具执行到一半，需要用户补一个参数或确认一下。旧版本的做法是服务端在一条长连接上直接反向发请求。新版本改成 Multi Round-Trip Requests：服务端把这次调用的结果标成 resultType: "input_required"，附上它要问的问题，然后结束这次请求；客户端拿到问题、问过用户之后，带着答案把原来的调用重发一次。

这样就不需要一直挂着一条双向流，符合整个协议「无状态」的方向。

7通知与订阅

服务端的东西可能变化（工具列表更新、资源内容改变）。客户端要感知这些变化，靠的是订阅：

  1. 客户端发 subscriptions/listen，在过滤条件里声明「我想听哪些事件」。
  2. 服务端回 notifications/subscriptions/acknowledged，确认它同意推送哪些。
  3. 之后有变化时，服务端在该流上发通知（如 notifications/tools/list_changed）。
  4. 客户端收到通知，重新调一次 tools/list 拿最新清单。

通知是尽力而为的：规范不保证每条都能送达，所以客户端还应该靠定期轮询来兜底。

8错误处理

协议层的错误用 JSON-RPC 标准错误码：

错误码含义
-32700解析错误（收到的不是合法 JSON）
-32600非法请求（结构不符合 JSON-RPC）
-32601方法不存在
-32602参数非法
-32603服务端内部错误
-32000 ~ -32099留给 MCP 自定义（如上面的版本不支持 -32004）

再次强调第 3 节那个区分：工具执行失败不是协议错误，它走正常的 result，用 isError: true 标记，因为那个信息是给模型看的。

9一句话总结

第 3 册 · 一句话总结

MCP 的消息就是 JSON-RPC 2.0 的三种报文 —— 带 id 的请求、带同 id 的响应、不带 id 的通知；一次工具调用就是「tools/list 拿清单 + tools/call 传参数」两次 JSON 往返；2026-07-28 版取消了握手和会话，每个请求在 _meta 里自带版本与能力，服务端可以无状态处理；传输层上，stdio 用「一行一条 JSON」分帧，Streamable HTTP 用 POST 加 Mcp-Method / Mcp-Name 头路由。
